SvelteKit app layout for remote functions, server-only code, database and auth

Observed September 26-27, 2026 (UTC). Research for Wayfinder ticket [#42](https://github.com/layerdbiz/tridentcubed/issues/42); it changes no code and does not choose a database or auth library. Sources are svelte.dev docs (via Context7 and direct fetch), the `sveltejs/cli` repository (`version-1` branch, read with `gh api`), the `sveltejs/kit` remote-functions RFC, and the local tree. Secondary write-ups were not used.

## Short answer

The straw-man from #7 holds. Five of seven lines are confirmed by the docs or the `sv` templates; two need amendments, neither structural: (a) remote functions are public endpoints, so a `+page.server.ts` guard does not protect them and every `.remote.ts` must authorize itself through `getRequestEvent().locals`; (b) `sv add lucia` no longer exists, the current template is `better-auth` on top of `drizzle`, and it writes `src/lib/server/auth.ts`, `src/lib/server/db/`, `src/hooks.server.ts` and `App.Locals` in `src/app.d.ts`. File-naming suffixes (`.types.ts`, `.schema.ts`, `<folder>.<role>.ts`) and folder-per-component are Trident conventions with no upstream guidance either way.

One local correction: `apps/app` is on `@sveltejs/kit` 2.50.2, not 2.70.x.

## What this means for `apps/app`

1. Add `src/hooks.server.ts` and an `App.Locals` declaration when auth lands; keep `src/lib/server/` for db and auth, as the `sv` templates do.
2. Keep `.remote.ts` outside `src/lib/server/`; they import from it instead.
3. Treat every remote function as a public endpoint: read `getRequestEvent().locals` and `error(401)` or `redirect` inside it. `+page.server.ts` guards protect pages, not data.
4. Guard per page or in the hook, not in `+layout.server.ts`.
5. Naming suffixes and folder-per-component are Trident's to keep; upstream is silent.
6. When the platform map picks auth, the `sv` reference to copy is `better-auth` + `drizzle`, not Lucia.
