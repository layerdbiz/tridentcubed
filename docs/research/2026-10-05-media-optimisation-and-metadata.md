Optimising 4K field photos and video on upload, and reading their metadata

Observed October 5, 2026. Research for ticket #124: how surveyors' 4K photos and video from iPhones and Android phones should be shrunk, described and stored when uploaded from a SvelteKit 3 PWA into Supabase. It changes nothing in the repo. Sources are Apple, Google (Android, Drive), Microsoft Graph, MDN and its browser-compat data, caniuse data, WebKit source and Bugzilla, Supabase docs and pricing, Cloudflare, Mux and Bunny pricing pages, the npm registry and the libraries' own READMEs. Apple Developer Forum threads are quoted only where Apple publishes nothing else; they are developer reports, not Apple statements, and are marked as such. Secondary blog posts were not used as evidence.

Terms used below. **EXIF** is the block of tags a camera writes into a JPEG or HEIC (capture time, GPS, orientation, camera model). **HEIC/HEIF** is Apple's default photo format since iOS 11; **HEVC (H.265)** is the matching video codec; **H.264** is the older, universally playable video codec. **Transcoding** means re-encoding a video into another codec or size. **TUS** is the resumable-upload protocol Supabase Storage implements. A **signed URL** is a time-limited link to a private file. **Origin image** is Supabase's billing unit for image transformations: one distinct source file, however many sizes are made from it.

## Short answer

Recommendation, **medium confidence**:

1. **Photos.** Upload the file the phone hands you, unchanged, over TUS into a private bucket, and let **Supabase image transformations** (Pro plan, $5 per 1,000 distinct images after the first 100 each month) make every display size through signed URLs. Supabase accepts HEIC as a source and returns JPEG/WebP, which also solves Android Chrome's inability to show HEIC. Do a small client-side JPEG preview (`createImageBitmap` → `OffscreenCanvas.convertToBlob` in a worker) only for instant UI; do not make the browser the thing that produces the stored copies.
2. **Metadata.** Read EXIF in the browser **before** upload with `exifr` (capture time, GPS, orientation) and save it to Postgres with the upload row. Treat it as best effort: iOS strips EXIF from photos taken by the in-browser camera and may strip location on library picks; Android hides photo GPS from apps by default. So also record the device clock and a Geolocation API fix (with consent) at upload time as the fallback for "when and where".
3. **Video.** Do not transcode in the browser for V1. Upload the original (an iPhone gives Safari the original HEVC `.mov`) over TUS; read duration, dimensions, rotation and creation date client-side with `mediabunny`. Supabase has no video processing, so when playback on every device matters, send a copy to **Cloudflare Stream** ($5 per 1,000 minutes stored per month, $1 per 1,000 minutes delivered, encoding free, 1080p output) or **Bunny Stream** (cheapest per GB) and keep the original in Supabase. Browser transcoding (WebCodecs via mediabunny) is real but H.264 *encoding* is missing on most iPhones; ffmpeg.wasm is a 31 MB download and "a lot slower than native".
4. **SvelteKit does nothing at runtime.** `@sveltejs/enhanced-img` is a build plugin for images on disk at build time; it cannot touch uploads.
5. **Backups to Drive/OneDrive** are feasible from a server job only with a company Google Workspace shared drive or a Microsoft 365 SharePoint/OneDrive for Business site; personal Drive/OneDrive needs a human's OAuth refresh token kept on the server.

Video location lives in a QuickTime metadata key, not EXIF: Apple's identifier `quickTimeMetadataLocationISO6709` is the string key `mdta/com.apple.quicktime.location.ISO6709` (an ISO 6709 string such as `+37.3318-122.0312+000.000/`) ([Apple AVFoundation](https://developer.apple.com/documentation/avfoundation/avmetadataidentifier/quicktimemetadatalocationiso6709)). Android's own API reads video location with no extra permission ([Android](https://developer.android.com/training/data-storage/shared/media)), so Android phones do not redact it the way they redact photo GPS. What to store per upload: `capturedAt` (EXIF `DateTimeOriginal` or QuickTime creation date, else the device clock at upload, with a flag saying which), `lat`/`lng` (EXIF GPS, the ISO 6709 key, or a Geolocation API fix taken at upload, again flagged), `orientation`, `width`/`height`, `durationSeconds`, `codec`, `mime`, `bytes`, and the device make/model when present.

## 6. SvelteKit and `@sveltejs/enhanced-img`

`@sveltejs/enhanced-img@1.0.0` (published 2026-10-01) is a Vite build plugin: "As a build plugin, `@sveltejs/enhanced-img` can only optimize files located on your machine during the build process." For "an image located elsewhere (such as a path served from your database, CMS, or backend)" the docs point to "loading images dynamically from a CDN", listing `@unpic/svelte` and provider libraries ([SvelteKit images](https://svelte.dev/docs/kit/images), checked 2026-10-05). It also "strips EXIF data for privacy" from the images it does process, which is one more reason it is the wrong tool for survey evidence. SvelteKit's runtime (remote functions, form actions, hooks) can *receive* an upload and forward it, but has no image or video processing of its own; the owner's recollection that "SvelteKit optimises uploads" is a build-time feature misremembered.

Feasibility: a nightly job that copies new originals from Supabase (server-side `download` with the secret key) into a Trident **Workspace shared drive** (service account) or a **SharePoint/OneDrive for Business** library (app-only `Sites.ReadWrite.All`) is routine. ## Open questions

- Does the iOS 17+ picker's "include location" option survive into the `File` Safari hands the page for library picks, and is it on by default? Only an on-device test with a geotagged photo answers it; the WebKit bug thread reports both outcomes across 2023.
- Does Android Chrome's file input hand over a photo with GPS redacted (as Android's scoped-storage rule implies) or not? Test on a Pixel and a Samsung with location tagging on; no Google source states Chrome's behaviour.
