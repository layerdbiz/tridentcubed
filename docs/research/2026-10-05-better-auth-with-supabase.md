Better Auth with Supabase: what it costs, and what the alternatives give up

Observed October 5, 2026. Research for the Report Generator V1 auth decision: the owner wants Better Auth; [2026-10-03-v1-architecture-research.md](2026-10-03-v1-architecture-research.md) recommended Supabase Auth. This file tests that doc's claim that "Better Auth's session cookie does not automatically authorize Supabase APIs; that route needs server-mediated access or an explicit token integration. Supabase's documented first-class external JWT providers do not currently include Better Auth." It changes nothing in the repo. Sources are Supabase, Better Auth, Svelte, Drizzle, Neon and PowerSync docs and source code, the npm registry, and GitHub issues on those projects' own repos. Secondary write-ups were not used as evidence.

Terms used below. **RLS** (row-level security) is Postgres filtering rows per query by policies that read the caller's identity. **JWT** is a signed token carrying claims such as `sub` (user id) and `role`; **JWKS** is the public-key list a verifier downloads to check signatures; **HS256** is the older shared-secret signing. Supabase's **service role / secret key** is the server credential whose Postgres role has `BYPASSRLS`, so it skips every policy.

## Short answer

The starting doc's claim holds, with one nuance it missed. Supabase's documented third-party providers are exactly Clerk, Firebase, Auth0, AWS Cognito and WorkOS ([overview](https://supabase.com/docs/guides/auth/third-party/overview)); Better Auth is not among them, and its session cookie means nothing to Supabase. The nuance: the Supabase Management API body for a third-party integration is a generic `{ oidc_issuer_url, jwks_url, custom_jwks }` ([OpenAPI spec](https://api.supabase.com/api/v1-json), `CreateThirdPartyAuthBody`), and Studio labels anything it does not recognise "Custom" ([`ThirdPartyAuthForm.utils.ts`](https://github.com/supabase/supabase/blob/master/apps/studio/components/interfaces/Auth/ThirdPartyAuthForm/ThirdPartyAuthForm.utils.ts)). Registering Better Auth's JWKS therefore looks mechanically possible, but it is undocumented, absent from Studio's "Add provider" menu, and impossible in the CLI's local stack, which only resolves the five named providers ([`jwks.ts`](https://github.com/supabase/cli/blob/develop/apps/cli/src/shared/auth/jwks.ts)). Treat it as a prototype question, not a plan.

Recommendation, **medium confidence**: if Better Auth is the owner's call, run **pattern (a)**: Better Auth owns identity in the Supabase Postgres via Drizzle; the SvelteKit server is the only Supabase client (secret key, server-side); RLS stays on and is enforced server-side through Drizzle's transaction-local claims wrapper as defence in depth; Storage is reached through server-created signed download and signed upload URLs. What this gives up is client-side Supabase access, which V1 does not need for data (the architecture doc already routes writes through server actions and a sync engine), but does need for **Realtime private channels**, which require a JWT Supabase can verify. That single gap is what the prototype must settle (section 7). If the team is not willing to carry that gap, Supabase Auth throughout (pattern c) remains the fewest-steps path, as the earlier doc said. Plain Postgres (Neon) plus Better Auth is viable but costs Storage, Realtime and TUS uploads, which V1 relies on.

## 2. The Better Auth side

- **Versions.** `better-auth@1.7.7` (2026-09-30), `@better-auth/cli@1.4.21`, `sv@1.1.0`, `@sveltejs/kit` latest `3.0.0` (`npm view`, 2026-10-05).
- **SvelteKit integration.** `svelteKitHandler({ event, resolve, auth, building })` in `hooks.server.ts`; `auth.api.getSession({ headers })` for `event.locals`; `createAuthClient()` from `better-auth/svelte` with `useSession()`; the `sveltekitCookies(getRequestEvent)` plugin needs "SvelteKit 2.20.0 and later" ([docs](https://www.better-auth.com/docs/integrations/svelte-kit)). The published `better-auth/svelte-kit` entry imports only `@sveltejs/kit` and `better-call` (tarball inspection).
- **Kit 3 peer dependency is behind.** `peerDependencies['@sveltejs/kit'] = '^2.0.0'` (optional). Issue [#10928](https://github.com/better-auth/better-auth/issues/10928) (open, 2026-08-22) and duplicate [#11586](https://github.com/better-auth/better-auth/issues/11586) (2026-10-04); PR [#11488](https://github.com/better-auth/better-auth/pull/11488) (2026-09-30, open) widens it to `^2.0.0 || ^3.0.0-0`, arguing the integration "relies only on `RequestEvent` and `cookies.set`". pnpm warns on an optional peer; npm errors. Remote-functions client integration is an open feature request, [#10555](https://github.com/better-auth/better-auth/issues/10555).
- **Drizzle adapter.** `drizzleAdapter(db, { provider: "pg" })`; schema via `npx auth generate` then `drizzle-kit generate/migrate`; `schemaName` supported for Postgres namespaces ([docs](https://www.better-auth.com/docs/adapters/drizzle)).
- **`sv add better-auth`** (from the `sv@1.1.0` bundle, since GitHub access to `sveltejs/cli` was blocked in this session): `unsupported("Requires SvelteKit")`; `if (!dependencyVersion("drizzle-orm")) dependsOn(ADDON_IDS.drizzle)`; reads the dialect from `drizzle.config.*` and maps `postgresql -> "pg"`; writes `.env`/`.env.example` with `BETTER_AUTH_SECRET` (and GitHub OAuth vars for `demo:github`); writes `src/lib/server/db/auth.schema.*` and an `auth:schema` script (`auth generate --config ... --output ...`); appends `svelteKitHandler` to `src/hooks.server.*`; adds `sveltekitCookies(getRequestEvent)` as the last plugin; optional demo login/register pages ([published docs](https://svelte.dev/docs/cli/better-auth)). It assumes Drizzle talks to the database directly, which fits Supabase's own Drizzle guide (pooler `DATABASE_URL`, [docs](https://supabase.com/docs/guides/database/drizzle)).
- **JWT plugin.** Issues "JWKS-verifiable JWTs for external services", separate from the session token; JWKS at `/jwks` (configurable); algorithms EdDSA (default), ES256, ES512, RS256, PS256; `jwks.remoteUrl` for an external signer; issuer and audience default to `BASE_URL`; `getSubject` defaults to the user id; `definePayload` adds claims; expiry default `"15m"`; token via `GET /token` (requires a session) or the `set-auth-jwt` header; verification example uses `jose.createRemoteJWKSet` ([docs](https://www.better-auth.com/docs/plugins/jwt), [`sign.ts`](https://github.com/better-auth/better-auth/blob/main/packages/better-auth/src/plugins/jwt/sign.ts) sets `kid` in the protected header, [`index.ts`](https://github.com/better-auth/better-auth/blob/main/packages/better-auth/src/plugins/jwt/index.ts) guards `/token` with `sessionMiddleware`). No OIDC discovery document comes from the jwt plugin alone; `@better-auth/oauth-provider` adds OAuth 2.1/OIDC on top of it (Context7, 1.5 release notes). Supabase's API accepts a bare `jwks_url`, so discovery may not be needed; unverified.
- **Bearer plugin** forwards the opaque session token, "intended only for APIs that don't support cookies"; it is not a JWT ([docs](https://www.better-auth.com/docs/plugins/bearer)).
- **UUID ids.** `advanced.database.generateId: "uuid"` makes ids UUIDs; needed because `auth.uid()` casts `sub` to `uuid` ([database concepts](https://www.better-auth.com/docs/concepts/database)).
- **Sessions.** 7-day expiry, `updateAge` sliding renewal, optional signed `cookieCache`, `httpOnly` + `secure` cookies, server-side `revokeSession*` ([session management](https://www.better-auth.com/docs/concepts/session-management), [cookies](https://www.better-auth.com/docs/concepts/cookies)).
- **Supabase in Better Auth's own material.** The [Supabase migration guide](https://www.better-auth.com/docs/guides/supabase-migration-guide) points Better Auth at the Supabase Postgres with `new Pool({ connectionString: DATABASE_URL })` and says it "doesn't currently cover migrating two-factor (2FA) or Row Level Security (RLS) configurations, both should be possible with additional steps". Issue [#1839](https://github.com/better-auth/better-auth/issues/1839) "Supabase Realtime + RLS support" (2025-03-16, closed "not planned") shows a user signing HS256 tokens with `SUPABASE_JWT_SECRET`, claims `role: "authenticated"`, `sub: user.id`, and passing them via `Authorization` and `supabase.realtime.setAuth()`; its two comments could not be read in this session. Discussion [#2520](https://github.com/better-auth/better-auth/discussions/2520) is only about migrating users off Supabase Auth.

## 3. The three production patterns

Evidence that each is "really used" is uneven. Pattern (c) is Supabase's documented default. Pattern (a) is what Better Auth's own migration guide and the Drizzle RLS docs describe. Pattern (b) exists as user reports (#1839, the Supabase discussions) and a generic API, not as a documented integration.

| | (a) Better Auth, server-mediated Supabase | (b) Better Auth JWT registered with Supabase | (c) Supabase Auth throughout |
| --- | --- | --- | --- |
| Identity authority | Better Auth tables in Supabase Postgres (Drizzle) | Better Auth; Supabase trusts its JWKS | Supabase Auth (`auth.users`) |
| Who talks to Supabase | SvelteKit server only, secret key | Browser + server, `createClient(..., { accessToken })` | Browser + server, Supabase SDK |
| RLS | On; enforced server-side by `set_config('request.jwt.claims', ...)` + `set local role authenticated` inside a Drizzle transaction ([Drizzle RLS](https://orm.drizzle.team/docs/rls)); the secret-key path bypasses it, so the wrapper is mandatory | Native `auth.uid()`/`auth.jwt()` on client calls, if `sub` is a UUID and `role: authenticated` is in `definePayload` | Native |
| Storage | Server issues `createSignedUrl` and `createSignedUploadUrl`; TUS accepts the signed upload token in `x-signature` ([resumable uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads)); object policies are server-only | Storage policies evaluate the Better Auth token | Policies or signed URLs |
| Realtime private channels | **Gap**: the browser needs a JWT Supabase can verify; the server would have to mint one (imported signing key, undocumented) or use (b) | `accessToken` is "also called on connect and on every heartbeat (default 25000ms)"; token must outlive the next heartbeat ([supabase-js types](https://github.com/supabase/supabase-js/blob/master/packages/core/supabase-js/src/lib/types.ts)); `role: authenticated` required ([discussion #28483](https://github.com/orgs/supabase/discussions/28483)) | Works out of the box |
| Local dev | Supabase CLI stack + Better Auth, no auth coupling | Not reproducible locally: CLI resolves only the five providers | CLI stack |
| Lock-in | Auth portable (own tables); Storage/Realtime are Supabase | Same, plus a Supabase-specific registration | Users in `auth.users`; migration guide exists but "will invalidate all active sessions" |
| MAU cost | None for auth; Supabase MAU meter unused | Third-Party MAU, same rate as MAU | 50k free / 100k Pro included |
| Residual risk | Every data path must go through the wrapper; one direct `db` query under the owner role skips RLS | Undocumented, could break silently; `kid` and algorithm acceptance (EdDSA vs ES256) unverified; 30-min key-rotation lag | Session rules tied to Supabase plans (time-box and inactivity limits "only available on Pro Plans and up", [sessions](https://supabase.com/docs/guides/auth/sessions)) |

Two further notes on (a). First, the Drizzle docs' `createDrizzle` wrapper runs `select set_config('request.jwt.claims', ...)`, `select set_config('request.jwt.claim.sub', ...)`, `set local role ...` and points at the [drizzle-supabase-rls](https://github.com/rphlmr/drizzle-supabase-rls) example; with Better Auth you build the claims object from `event.locals.user` instead of decoding a Supabase JWT, so no token is involved at all. Second, with Better Auth owning identity, the Supabase Auth service keeps running but is unused ("It is not possible to disable Supabase Auth"); the `auth.users` table stays empty.

## 4. Plain Postgres (Neon) + Better Auth

- Neon ships "Managed Better Auth", "powered by Better Auth", "version 1.4.18", AWS regions only, data in a `neon_auth` schema "compatible with Row Level Security (RLS) policies", MAU included (Free up to 60,000), quick starts for Next.js, React and TanStack Router only; self-hosting Better Auth is the documented path for "custom plugins, hooks, and options not yet supported" ([Neon Auth overview](https://neon.com/docs/auth/overview)).
- Neon's Data API accepts an `external` provider with "the JWKS URL supplied by your auth service" plus optional `jwt_audience`, and reads the role from a configurable claim path; RLS uses `auth.user_id()` from `pg_session_jwt` ([manage](https://neon.com/docs/data-api/manage), [custom providers](https://neon.com/docs/data-api/custom-authentication-providers), [pg_session_jwt](https://neon.com/docs/extensions/pg_session_jwt)). So a self-hosted Better Auth JWKS is a first-class input on Neon where it is undocumented on Supabase.
- Gained: branch-per-preview databases with auth state, Better Auth as a native citizen, no unused auth service. Given up: object storage (none; you add R2/S3 and write your own signed-URL layer), Realtime, TUS resumable uploads, Studio's policy editor, and the Supabase Storage CDN economics the earlier doc priced. The sync layer is neutral: PowerSync verifies "JWKS on a public URL" from any issuer with `sub`, `aud`, `iat`, `exp` and expiry of 24 hours or less ([PowerSync custom auth](https://docs.powersync.com/installation/authentication-setup/custom)).

## 5. Offline and PWA sessions

- **Supabase Auth (c).** Access token default 1 hour; "refresh tokens never expire but can only be used once", with a 10-second reuse interval and parent-token tolerance so that "when the client comes back online, it will attempt to use the refresh token that was already used" without losing the session ([sessions](https://supabase.com/docs/guides/auth/sessions)). `supabase-js` ticks every 30 s, refreshes within 3 ticks (90 s margin) and `_recoverAndRefresh()` refreshes an expired stored session on startup ([constants.ts](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/lib/constants.ts), [GoTrueClient.ts](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueClient.ts)). A device offline for hours resumes without re-login unless a Pro-plan time-box or inactivity timeout is set. Private Realtime channels drop at JWT expiry and need a new token on reconnect ([Realtime authorization](https://supabase.com/docs/guides/realtime/authorization)).
- **Better Auth (a).** The session is a 7-day `httpOnly` cookie; nothing expires on the device while offline, and the first online request renews it under `updateAge`. The offline queue carries no token; the server checks the cookie when the replay arrives. The lock-out window after revocation is bounded by `cookieCache.maxAge` if caching is on.
- **Better Auth JWT (b).** Tokens live 15 minutes by default and `/token` requires a live session, so after hours offline the Supabase client's `accessToken` callback must fetch a fresh token on reconnect; Supabase itself is unreachable offline, so no data is lost, but the callback must handle the first call failing.

## 6. Where the sources adjust the 2026-10-03 doc

1. "First-class external JWT providers do not currently include Better Auth": correct. Add: the Management API and Studio data layer are generic (`jwks_url`, `custom_jwks`), so a registration is possible but undocumented, not offered in Studio's menu, and not reproducible in local dev.
2. "Server-mediated access or an explicit token integration": correct, and the server-mediated path has a documented shape, Drizzle's `set_config` transaction wrapper, so RLS need not be "mostly off" under Better Auth.
3. Not in the earlier doc: `better-auth@1.7.7` still declares `@sveltejs/kit ^2.0.0`; the fix is an open PR. A Kit 3 project installs with a pnpm warning today.
4. Not in the earlier doc: Supabase's shared-secret path (how older community answers mint tokens) is "Not recommended for production"; only asymmetric keys with `kid` qualify as third-party tokens.
5. The sv add-on description is confirmed and sharper: it pulls in the drizzle add-on when `drizzle-orm` is absent and generates the auth schema through `auth generate`.

## Open questions

- Does Supabase accept a `POST .../third-party-auth` with a Better Auth `jwks_url` (ES256, `kid` present) and then honour `role: authenticated` and `auth.uid()` on Data API, Storage and Realtime? Only a prototype against a real project can answer; the docs promise nothing for unlisted issuers, and the CLI cannot emulate it.
- Does Supabase verify EdDSA (Better Auth's default) for third-party tokens, or must `keyPairConfig.alg` be `ES256`/`RS256`? Not stated anywhere.
- Can a server legitimately mint Supabase-verifiable tokens with an imported signing key (documented as supported for key rotation, not for external minting)? If yes, pattern (a) closes its Realtime gap without third-party registration; Supabase has not said so.
- What did the two comments on better-auth#1839 say before it was closed "not planned"? Unreadable here (GitHub API access blocked for that repo in this session).
- When will better-auth publish a release whose peer range includes `@sveltejs/kit@3`? PR #11488 was open on 2026-10-05.
- Prototype must prove, for pattern (a): one `createDrizzle`-style helper is the only query path; a direct owner-role query is caught by lint or test; signed upload URL + TUS resume works from a Better Auth session; a revoked Better Auth session cannot replay a queued write; and whichever Realtime token route is chosen survives a 25 s heartbeat and a reconnect after hours offline.
