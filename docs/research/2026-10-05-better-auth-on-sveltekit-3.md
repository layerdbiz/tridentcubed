Better Auth on SvelteKit 3, and Supabase third-party auth, re-checked

Observed October 5, 2026, for wayfinder ticket #114. This file re-verifies the claims in [2026-10-05-better-auth-with-supabase.md](2026-10-05-better-auth-with-supabase.md) that can go stale (package versions, peer ranges, open PRs and issues, Supabase's provider list) and extends them with a hands-on test: a fresh SvelteKit 3 project scaffolded with `sv@1.1.0`, `sv add better-auth` run on it, then `npm install`, `pnpm install`, `auth generate`, `svelte-check` and `vite build`. Sources are the npm registry, GitHub pages of `better-auth/better-auth`, `sveltejs/cli`, `supabase/supabase`, `supabase/cli` and `supabase/auth` (read through the web, since the GitHub API is limited to this repository in this session), svelte.dev, better-auth.com and supabase.com. It changes nothing else in the repo.

Terms. A **peer dependency** is a package's statement of which versions of another package it works with; `npm` refuses to install when the statement is violated, `pnpm` only warns. **JWKS** is the public-key list a verifier downloads to check token signatures. **RLS** is Postgres filtering rows per query by the caller's identity.

## Short answer

Nothing material has moved since the earlier file, and the hands-on test shows where it bites. `better-auth@1.7.7` (2026-09-30) is still the latest release and still declares `@sveltejs/kit: ^2.0.0` as an optional peer; PR [#11488](https://github.com/better-auth/better-auth/pull/11488), which widens it to `^2.0.0 || ^3.0.0-0`, is **still open**, and the issue it fixes, [#10928](https://github.com/better-auth/better-auth/issues/10928), is still open with a fresh duplicate closed on 2026-10-04. In practice `sv add better-auth` on a Kit 3 project scaffolds correctly (Kit 3 idioms throughout: `#lib`, `$app/env`, `$app/env/private`, `Handle` from `@sveltejs/kit/hooks`), and once installed it type-checks with zero errors and builds. The only blocker is the install step itself: `npm install` fails with `ERESOLVE` (reproduced here, and reported to the Svelte CLI team as [sveltejs/cli#1403](https://github.com/sveltejs/cli/issues/1403), closed "not planned" on 2026-10-04 because the fix belongs to Better Auth); `pnpm install`, which this repo uses, succeeds with one "unmet peer" warning. The `sveltekitCookies(getRequestEvent)` plugin requirement is unchanged and is what makes cookies work from Kit's server code, including remote functions, since Kit lets `form` and `command` write cookies. The remote-functions client request [#10555](https://github.com/better-auth/better-auth/issues/10555) is open with an unreviewed PR [#11419](https://github.com/better-auth/better-auth/pull/11419). `generateId: "uuid"` with the Drizzle adapter produced `uuid("id").default(sql\`pg_catalog.gen_random_uuid()\`)` columns in this test. On the Supabase side nothing changed: five named providers, the same generic Management API body, Studio's menu without a custom entry, and a CLI resolver with five branches and no generic one. The two comments on better-auth#1839 remain unreadable here.

For the map's decision line: Better Auth on Kit 3 works today with pnpm and a peer warning; expect the warning to disappear in a patch release once #11488 merges, and treat the npm failure as the reason not to use `npx sv create --add better-auth` with npm as the installer.

## 5. Which claims of the earlier file changed

Still hold, re-verified today: `better-auth@1.7.7` latest; peer `@sveltejs/kit ^2.0.0` optional; #11488 open, #10928 open, #11586 a closed duplicate; #10555 open; `sveltekitCookies(getRequestEvent)` requires Kit 2.20+ and must be last; `generateId: "uuid"` yields database-generated UUIDs on Postgres; Supabase's five providers, generic Management API body, Studio `'custom'` fallback without a menu entry, CLI resolver with five branches; EdDSA unproven; #1839 comments unreadable.

Changed or sharpened:

1. "A Kit 3 project installs with a pnpm warning today" is now demonstrated, and the npm case is worse than "errors": `sv create --add better-auth` with npm as installer cannot complete, per the reproduction and [sveltejs/cli#1403](https://github.com/sveltejs/cli/issues/1403), which the CLI team closed as Better Auth's problem.
2. The earlier file described the add-on's output from the `sv@1.1.0` bundle in Kit 2 terms (`$lib`, `src/hooks.server.*`). On a Kit 3 project the same add-on writes Kit 3 idioms (`#lib`, `$app/env`, `$app/env/private`, `src/env.ts` with `defineEnvVars`, `Handle` from `@sveltejs/kit/hooks`, `better-auth/minimal`), and the result type-checks and builds.
3. The Better Auth CLI is now the npm package `auth` (`auth generate`); the earlier file's `npx auth generate` was right, and the add-on installs `auth ^1.6.24` explicitly.
4. The default generated schema uses `text` ids; `generateId: "uuid"` is an explicit opt-in that the add-on does not set. Trident must add it before the first migration if `auth.uid()` on Supabase is ever wanted.
5. New: PR [#11419](https://github.com/better-auth/better-auth/pull/11419) exists for #10555, unreviewed; and Kit's own rule that `form`/`command` may write cookies means the existing plugin should already cover remote functions without that PR.
6. New: Supabase lists EdDSA as "Coming soon" for its own keys, which makes it even less likely that EdDSA third-party tokens verify today; pick ES256 in `keyPairConfig`.

## Open questions

- When does #11488 merge and ship, and as `^3.0.0-0` or `^3.0.0`? Until then pin pnpm (this repo already does) and expect the single peer warning.
- Does `auth.api.signInEmail` inside a Kit 3 `command` set the cookie through `sveltekitCookies` end to end? The docs' rule and the plugin source say yes; not executed here.
- Everything about Supabase accepting a Better Auth JWKS (registration via the API, `role`/`sub` handling, EdDSA vs ES256, Realtime) is unchanged from the earlier file and still needs a prototype against a real project; nothing on supabase.com moved in the last month.
- What the two comments on better-auth#1839 said: needs API access to `better-auth/better-auth` or a browser.
- The `auth` CLI's "Drizzle schema mismatch" error on first run is noise; whether it also fires when the schema exists but drifts (and whether it blocks) was not tested.
