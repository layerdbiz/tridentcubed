## 2. Vite+ in a pnpm monorepo

**Wraps, does not replace, pnpm.** "Commands such as `vp install` use the project's selected package manager." Selection order: explicit override, `VP_PACKAGE_MANAGER`, the `packageManager` field, `devEngines.packageManager`, lockfile/config files, then defaults; with none present "`vp` falls back to `pnpm` by default". Vite+ "automatically downloads the matching package manager" ([guide/env](https://viteplus.dev/guide/env), [guide/install](https://viteplus.dev/guide/install), read 2026-09-18). Trident's root `"packageManager": "pnpm@9.15.4"` would be honored. `pnpm-workspace.yaml` stays; it is the workspace definition pnpm reads. One documented conflict: "When both pnpm and Vite+ manage Node.js, they can download the same version separately or select different versions"; the docs recommend pnpm's `runtimeOnFail: ignore`, or `vp env off` to prefer system tools ([guide/env](https://viteplus.dev/guide/env)).

**Task runner (Vite Task) does have a dependency graph and a cache.**

**Coexistence with Turborepo.** Neither viteplus.dev nor the migration guide mentions Turborepo or Nx (checked [guide/run](https://viteplus.dev/guide/run), [guide/monorepo](https://viteplus.dev/guide/monorepo), [guide/migrate](https://viteplus.dev/guide/migrate)). `vp migrate` has no rule that reads or removes `turbo.json`. Users do run `vp` under Turborepo: [issue #2697](https://github.com/voidzero-dev/vite-plus/issues/2697) (2026-09-14, vite-plus 0.3.0) reports terminal-escape noise "when executing vite-plus builds through Turborepo's PTY"; it was closed as not planned on 2026-09-16, so that cosmetic issue stands. Coexistence is therefore possible in the direction "Turborepo orchestrates, package scripts call `vp build`/`vp test`", with the two caches independent. The reverse (Vite Task calling `turbo`) is unverified.

Turborepo's own latest is 2.11.2 (npm, 2026-09-18); Trident is on 2.8.3.

## 3. Formatting (Oxfmt vs Prettier)

**Options.** Oxfmt's config reference documents every setting Trident uses: `useTabs` (default false), `singleQuote` ("Available for JS, JSX, TS, TSX, CSS, Less, SCSS, Markdown, MDX, YAML, Handlebars, and Svelte"), `trailingComma` (`"all" | "es5" | "none"`, default `"all"`), `printWidth` (default 100), `singleAttributePerLine` ("Applies to JSX, TSX, HTML, Angular, Vue, MJML, and Svelte"), plus `overrides` and `ignorePatterns` ([oxc.rs config-file-reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference), read 2026-09-18). Oxfmt "matches Prettier's JavaScript formatting... any formatting differences are considered bugs" and "now passes 100% of Prettier's JavaScript and TypeScript conformance tests" ([oxc.rs formatter](https://oxc.rs/docs/guide/usage/formatter)). `npx oxfmt --migrate=prettier` converts `.prettierrc` ([migrate-from-prettier](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier)). Under Vite+ the settings go in the `fmt` block of root `vite.config.ts`; "We do not recommend using `.oxfmtrc.json` with Vite+" and "Vite+ does not currently support nested format configuration", so per-package differences need `fmt.overrides` ([guide/fmt](https://viteplus.dev/guide/fmt)).

**Svelte files.** Supported, but not natively: the language-support page classes `.svelte` as "Prettier-backed" and notes it "additionally requires the `svelte` package to be installed and the `svelte` option to be enabled"; Prettier-backed formats "require Node.js and are only available with the `oxfmt` npm package" ([language-support](https://oxc.rs/docs/guide/usage/formatter/language-support.html)). Mechanism: Oxfmt bundles `prettier-plugin-svelte` (tracking [issue #19715](https://github.com/oxc-project/oxc/issues/19715), opened 2026-02-25, still open, Svelte item checked; PR [#21700 "Experimental .svelte support"](https://github.com/oxc-project/oxc/pull/21700) merged 2026-05-11, shipped in oxfmt 0.49.0 the same day). `oxfmt@0.68.0` declares `peerDependencies: { svelte: ^5.0.0 }` (npm, 2026-09-14). Svelte options available: `allowShorthand`, `indentScriptAndStyle`, `sortOrder` ([config reference](https://oxc.rs/docs/guide/usage/formatter/config-file-reference)). The compatibility matrix marks Svelte and SvelteKit as **Partial** for Oxfmt ([oxc.rs/compatibility](https://oxc.rs/compatibility.html)). Generic Prettier plugins are "not supported (though some popular plugins have been implemented natively)" ([migrate-from-prettier](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier)).

**Tailwind class sorting.** Built in as `sortTailwindcss` ("Disabled by default", "Based on prettier-plugin-tailwindcss", limitation: "Regex patterns for `attributes` and `functions` are not supported"), with a `stylesheet` path option that maps to Trident's `tailwindStylesheet: "./src/app.css"` ([sorting](https://oxc.rs/docs/guide/usage/formatter/sorting.html)). Whether sorting applies inside `.svelte` markup: issue #19715 states the bundled Svelte path "integrates with existing oxc_formatter features like `sortImports` and `sortTailwindcss`"; the per-language table on oxc.rs does not list it, so treat Svelte-markup sorting as **verified by issue text only**. A related bug, [#22697](https://github.com/oxc-project/oxc/issues/22697) (oxfmt 0.51.0, 2026-05-24: whitespace in Svelte `class` attributes with `sortTailwindcss` on), was closed as not planned on 2026-06-29. Note Trident's stylesheet path is relative to the config file; with a single root `fmt` block that path has to be resolved per app via `fmt.overrides` or a workspace-root stylesheet (unverified whether overrides accept `sortTailwindcss`).

**Verdict.** Oxfmt can honor tabs, single quotes, no trailing commas, width 100 and single-attribute-per-line, and replaces `prettier-plugin-tailwindcss` for JS/TS. For `.svelte` it still runs Prettier + `prettier-plugin-svelte` under the hood, marked experimental/partial. The only way to know whether Trident's `.svelte` output is byte-identical is a `vp fmt --check` pilot on the existing tree. Until that passes, Prettier stays.

## 4. Linting (Oxlint)

- Oxlint lints "Framework files (`.vue`, `.svelte`, `.astro`) by linting only their `<script>` blocks"; the compatibility page says "Vue, Svelte, Angular, Ember, Nuxt, Astro, SvelteKit, and Analog: No template linting yet" and marks Svelte/SvelteKit **Partial** ([oxc.rs linter](https://oxc.rs/docs/guide/usage/linter), [compatibility](https://oxc.rs/compatibility.html), read 2026-09-18).
- Default rule set "prioritizes high-signal correctness checks"; plugins built in for ESLint core, TypeScript (including type-aware via tsgolint), React, Jest, Vitest, Import, Unicorn, jsx-a11y. JS plugins for ESLint-plugin compatibility are **alpha** ([oxc.rs linter](https://oxc.rs/docs/guide/usage/linter)). `eslint-plugin-svelte` therefore has no native equivalent; running it through the alpha JS-plugin bridge is unverified.
- Known Svelte wrinkle: `vp create svelte` + `vp check` reported "'$props' is not defined" from `no-undef` on `.svelte` files ([vite-plus #1967](https://github.com/voidzero-dev/vite-plus/issues/1967), 2026-06-28, PR #2192 linked). Any Trident config must disable `no-undef` for `.svelte` or declare rune globals.
- Under Vite+, lint settings live in the `lint` block; "Vite+ does not currently support nested lint configuration" ([config/lint](https://viteplus.dev/config/lint)). `typeAware`/`typeCheck` use "tsgolint on top of the TypeScript 7 (aka TypeScript Go) toolchain" ([guide/lint](https://viteplus.dev/guide/lint)); whether tsgolint type-checks `.svelte` script blocks is unverified, and `vp check` has no documented hook for `svelte-check` ([guide/check](https://viteplus.dev/guide/check)).

**Net gain given no linter today:** correctness linting of `.ts` files and Svelte `<script>` blocks at near-zero config, with no template rules. `svelte-check` remains the only template/type checker and must keep running outside `vp check`.

## 5. Testing (Vitest for Svelte 5 under Vite+)

- Vite+ 0.3.3 bundles Vitest 4.1.11; tests import from `vite-plus/test` (browser subpaths `vite-plus/test/browser*`), config goes in the `test` block of `vite.config.ts` ("Using a separate `vitest.config.ts` file is discouraged"), and "`vp test` does not stay in watch mode by default" ([guide/test](https://viteplus.dev/guide/test)). Browser providers (Playwright/WebdriverIO) "remain opt-in dependencies" ([guide/migrate](https://viteplus.dev/guide/migrate)).
- Monorepo: `vp test` at the root delegates to Vitest and ignores per-package configs; the maintainer-recommended pattern is `vp run test -r` ([discussion #1216](https://github.com/voidzero-dev/vite-plus/discussions/1216), reply 2026-04-03).
- Svelte 5 guidance ([svelte.dev/docs/svelte/testing](https://svelte.dev/docs/svelte/testing)): "If you're using Vite (including via SvelteKit), we recommend using Vitest"; set `resolve: process.env.VITEST ? { conditions: ['browser'] } : undefined`; for components "you need to set up a DOM environment" (`environment: 'jsdom'` or `// @vitest-environment jsdom`); runes work in tests "as long as the filename includes `.svelte`"; effects must be wrapped in `$effect.root` and flushed with `flushSync()`; `@testing-library/svelte` recommended for component tests. The Svelte docs do not mention Vitest Browser Mode.
- Browser mode alternative: `vitest-browser-svelte` 3.1.0 (npm 2026-09-04, peers `vitest ^4 || ^5`, `svelte ^3||^4||^5`) renders components in Vitest Browser Mode; Vitest docs recommend Playwright as provider ([vitest.dev/guide/browser](https://vitest.dev/guide/browser/)). Playwright is not installed in Trident, so jsdom is the lower-cost starting point; browser mode is a later add.
- With SvelteKit the `sveltekit()` plugin is already in each app's `vite.config`, so Vitest reuses it; per-app `test` blocks are needed because Trident's Vite configs are per app, which is exactly the case `vp run test -r` covers.

## 7. Migration guide applied to this repo

From [guide/migrate](https://viteplus.dev/guide/migrate) (read 2026-09-18):

1. Prerequisites the guide imposes: "Upgrade to Vite 8+ and Vitest 4.1+ first". For Trident that is, per app: `vite ^7.3.1 → ^8`, `@sveltejs/vite-plugin-svelte ^6.2.4 → ^7`, `@sveltejs/kit ^2.50.2 → ≥2.53`, and checking `@tailwindcss/vite` 4.1.18 against Vite 8 (or moving to 4.3.x). This step is independent of Vite+ and is where the Vite 8 + Svelte known issues (#1143) surface.
2. "For a monorepo, the target must be the workspace root", because migration "updates the package-manager configuration, the catalogs, and the lockfiles that all members share". So `vp migrate` runs at Trident's root, never in `apps/site` alone.
3. What it does: "Updates project dependencies", "Rewrites imports where needed", "Merges tool-specific config into `vite.config.ts`", "Updates scripts to the Vite+ command surface", "Can set up commit hooks", "Can write agent and editor configuration files", "Formats the migrated project". It consolidates "Vite, Vitest, Oxlint, Oxfmt, ESLint, Prettier, and tsup setups"; the page does not spell out what happens to `.prettierrc` or Prettier plugins, so expect a generated root `fmt` block and verify it by hand (Trident's tabs/quotes/width settings and the Svelte + Tailwind pieces described in section 3). "Most projects will require further manual adjustments after running `vp migrate`."
4. pnpm specifics: "keep the `vite`, `vitest` dependency entries configured by `vp migrate` so the workspace aliases and overrides stay effective" (Vite+ aliases `vite` to `@voidzero-dev/vite-plus-core`, visible in the npm `dependencies` of `vite-plus@0.3.3`).
5. Verify with `vp install`, `vp check`, `vp test`, `vp build` (or `vp pack` for libraries). For Trident `vp build` at the root needs `defaultPackage` or `-C apps/<app>` ([config/](https://viteplus.dev/config/)), and `packages/ui` keeps `svelte-package`, not `vp pack`.
6. Hooks: Husky/lefthook/simple-git-hooks are "left unchanged" with warnings; Trident has none, so `vp hooks enable` + a `staged` block would be a net addition, not a migration.

What `vp migrate` would **not** touch, by the absence of any rule in the guide: `turbo.json` and the `turbo` devDependency; `packages/tools` bins (`barrels`, `symlinks`, `stories`, `sheetari`, `workspace`) and the root scripts that call them; `svelte-package`, `svelte-check` and `svelte-kit sync` scripts; `pnpm-workspace.yaml`; Storybook. The `//#barrels` → `build` dependency would have to be re-expressed by hand as a Vite Task if Vite Task ever replaced Turborepo, and the env isolation default (section 2) means any generator reading env vars needs an `env`/`untrackedEnv` entry.
