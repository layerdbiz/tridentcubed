Typed report definitions: shape, cross-references and layout

Observed October 5, 2026, on branch `docs/48-report-definitions-nnippn` at `a7c1f46`. Research for Wayfinder ticket [#92](https://github.com/layerdbiz/tridentcubed/issues/92) (map [#1](https://github.com/layerdbiz/tridentcubed/issues/1), blocking [#48](https://github.com/layerdbiz/tridentcubed/issues/48)); it writes no application code. Sources are the TypeScript handbook and release notes on typescriptlang.org, svelte.dev's remote-functions page, orm.drizzle.team, the svelte-check README, this repo, and an experiment run against the installed `typescript@6.0.2` (`/opt/node-tools/node_modules/typescript`) in the session scratchpad. Secondary write-ups were not used as evidence; Matt Pocock's own pages are cited only where read directly.

## Short answer

Author each entity kind as an array literal written `as const satisfies readonly <Row>[]`, derive the id unions with `(typeof rows)[number]['id']`, and thread the panel- and page-id unions into the input row type as type parameters. This is the only one of the four shapes that keeps literal ids *and* checks every row *and* rejects excess properties (section 1, verified against TS 6.0.2). A dangling `panel` or `outputToPages` id is then a compile error with a "Did you mean" hint; `reference` (input to input) cannot be checked the same way because the array's type would reference itself, so it gets a one-line post-hoc conditional type instead (section 2). Keep one file per entity kind (`panels.ts`, `pages.ts`, `inputs.ts`) plus `types.ts` and an `index.ts` that exports the derived lookups; a per-panel vertical slice breaks the id derivation and is not what the UI consumes (section 3). The 36 instructions rows become JSDoc on the interface fields: TypeScript's quick info surfaces the interface field's JSDoc on a property inside a `satisfies`-checked literal, identically to a colon-annotated one (section 4). Static data needs no remote function; the pages import the module and `fetchProjectDefinitions` goes away, with `prerender` as the fallback if a server-only read ever returns (section 5). The flat rows seed Drizzle with `db.insert(table).values(rows)` and the `as const` unions feed `text({ enum })`/`pgEnum` directly (section 6).

## 1. `satisfies` vs `as const` vs `as const satisfies` vs a typed array

| Shape | Checks every row | Rejects excess property | Keeps literal `id` | Evidence |
| --- | --- | --- | --- | --- |
| `const rows: readonly Row[] = [...]` | yes | yes (`TS2353`) | **no**: `(typeof rows)[number]['id']` is `string` | [Excess property checks](https://www.typescriptlang.org/docs/handbook/2/objects.html): "Object literals get special treatment and undergo excess property checking when assigning them to other variables"; experiment `b-typed.ts` |
| `[...] satisfies readonly Row[]` | yes | yes | **no**: a literal in a `string`-typed slot widens; `const check: A = 'anything-goes'` compiled | [TS 4.9 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html): `satisfies` validates "without changing the resulting type of that expression", but the resulting type is still the widened inferred one; experiment `a-satisfies.ts` |
| `[...] as const` | **no** | **no** | yes | [TS 3.4 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html): "no literal types in that expression should be widened", "object literals get `readonly` properties", "array literals become `readonly` tuples"; nothing is compared against a type |
| `[...] as const satisfies readonly Row[]` | yes | yes (`TS2353`) | yes | both of the above; experiment `c-inputs.ts` reports `'typo' does not exist in type 'InputDefinitionType<...>'` and `Type '"sidebar"' is not assignable to type 'OutputPageSectionType'` while `(typeof inputs)[number]['id']` is the union of the seven literal ids |

Two consequences of `as const` that the row types must absorb. Every array property becomes a `readonly` tuple, so the row interface must declare `readonly string[]`, `readonly PageId[]` and so on; today's `options: string[]`, `outputToPages: string[]`, `reference: string[]` (`apps/app/src/routes/(app)/projects/projects.types.ts:205,212,216`) would reject the literal. Since TS 5.3 a readonly tuple may satisfy a *mutable* array type ([Pocock, "The TypeScript 5.3 feature they didn't tell you about"](https://www.totaltypescript.com/the-typescript-5-3-feature-they-didn-t-tell-you-about): "`const array = ["a", "b", "c"] as const satisfies string[]` ... would error in 5.2, but is allowed in 5.3!"), so the `readonly` on the outer `readonly Row[]` is optional on TS 6, but the *field* types still need `readonly` or the derived element type is unusable where a mutable array is expected. Writing `readonly` on the interface is the honest choice: definitions are not mutated. Second, `as const` applies only to literal expressions ("can only be applied to a string, number, boolean, array, or object literal", TS 3.4 notes), so no row may be built by a helper call; a `create*` factory would have to be a `const` type-parameter generic ([TS 5.0 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html): a `const` modifier on a type parameter gives "`const`-like inference" without `as const` at the call site). Pocock's own rule for the operator ([Clarifying the `satisfies` operator](https://www.totaltypescript.com/clarifying-the-satisfies-operator)): use `satisfies` when "You want the EXACT type of the variable, not the WIDER type" and "The type is complex enough that you want to make sure you didn't mess it up". A catalogue whose ids become unions is exactly that case.

## 2. Cross-references that fail the type check

Pattern, as run in the experiment (`scratchpad/tsx/{types,panels,pages,c-inputs}.ts`):

```ts
// panels.ts
export const panels = [...] as const satisfies readonly PanelDefinitionType[];
export type PanelIdType = (typeof panels)[number]['id'];
// pages.ts: same, exporting PageIdType
// types.ts
export interface InputDefinitionType<PanelId extends string = string, PageId extends string = string> {
	readonly panel: PanelId;
	readonly outputToPages: readonly PageId[];
	readonly reference: readonly string[]; // see below
	// ...
}
// inputs.ts
export const inputs = [...] as const satisfies readonly InputDefinitionType<PanelIdType, PageIdType>[];
export type InputIdType = (typeof inputs)[number]['id'];
type ReferencedIdType = (typeof inputs)[number]['reference'][number];
export const referencesResolve: [ReferencedIdType] extends [InputIdType] ? true : never = true;
```

`(typeof x)[number]` is the handbook's own idiom ([Indexed access types](https://www.typescriptlang.org/docs/handbook/2/indexed-access-types.html): "using `number` to get the type of an array's elements. We can combine this with `typeof`"). Results on TS 6.0.2:

- `panel: 'PANEL-009'` → `TS2820: Type '"PANEL-009"' is not assignable to type '"PANEL-001" | "PANEL-002"'. Did you mean '"PANEL-001"'?`; `outputToPages: ['PAGE-002']` → the same error class naming the valid page ids. The error points at the offending row and column, which is what "an agent reads a definition in one file open" needs.
- `reference` **cannot** be typed `readonly InputIdType[]` inside the same `satisfies`: `InputDefinitionType<PanelIdType, PageIdType, InputIdType>` produced `TS4109: Type arguments ... circularly reference themselves`, `TS7022: 'inputs' implicitly has type 'any'`, and the whole array degraded to `any`, silently disabling every other check. The post-hoc conditional above restores it: `reference: ['ORG-999']` → `TS2322: Type 'true' is not assignable to type 'never'` on the `referencesResolve` line; fixing the id clears it. The message does not name the bad id, so keep a comment on that line saying what it guards. A unit test (`inputs.test.ts`, per root `AGENTS.md:99`) can name the offender at runtime; the type keeps `svelte-check` red.
- Panel-level `reference` (`projects.types.ts:234`) today is empty in all 12 rows and can stay `readonly string[]`.

Cost. The definition files import each other's *types* only (`import type`), so there is no runtime cycle, but the dependency direction is fixed: `panels.ts` and `pages.ts` must not import from `inputs.ts`. Generic parameters on `InputDefinitionType` make every consumer that spells the type write `InputDefinitionType` (defaults to `string`) or the exported `InputRowType = (typeof inputs)[number]`; readers should prefer the latter. Scale is not a concern: the full 84/12/20 catalogue generated from the JSON snapshot (48 KB of source, 92-line `inputs.ts`) type-checks in `Check time: 0.32s`, 6,497 types, 4,477 instantiations (`tsc --extendedDiagnostics`). Today's rows cross-reference by **title** (`projects.remote.ts:58` reads `value.panel || value.section`; `projects.schema.ts:23-41` groups by `panel.title`; `inputs.json` says `"panel": "Organization"`, `"outputToPages": "Cover, Introduction"`). The experiment mapped titles to ids while generating and found every title resolves (0 unmatched panels, pages or references; the five `reference` rows are `PRJ-002 -> CLT-003, PRJ-004, PRJ-001`, `PRJ-003 -> TIM-002`, `INSP-007 -> INSP-006`, `DAM-007 -> DAM-006`, `DSC-007 -> DSC-006`). Switching the stored value from title to id is a one-time rewrite that lands with the catalogue; `createProjectSchema` then groups by `panel.id` and `getPanelDefinition(schema, 'Custom')` (`[projectId]/+page.svelte:35`) becomes a lookup by id or a derived constant.

## 3. File layout

| Layout | Id derivation | What the UI reads | Verdict |
| --- | --- | --- | --- |
| One file per entity kind: `types.ts`, `panels.ts`, `pages.ts`, `inputs.ts`, `index.ts` | Direct: each union is `(typeof rows)[number]['id']` of one array | `index.ts` exports `inputsByPanel`, `pagesById`, the arrays and the unions | **Recommended** |
| One file per panel (vertical slice: the panel row plus its ~7 inputs, 12 files) | Indirect: `PanelIdType` needs a union across 12 files, and each file's inputs need `PageIdType` and the *other* panels' ids for `reference`; the union is assembled in a barrel, which the barrels generator owns (root `AGENTS.md:79`) and would need to learn to write as `as const` tuples | Needs the barrel to concatenate before grouping; grouping-by-panel is then trivially the file | Costs the derivation and fights the generator; the three `PRJ`/`CLT`/`TIM` cross-panel references show panels are not closed slices |
| One file holding all 116 rows | Direct | Same as per-kind | Works, but the 84 input rows at ~500 chars each dominate the file; `instructions` JSDoc and the three arrays are easier to read as four short files |

Pocock's writing on vertical slices was searched for on mattpocock.com, aihero.dev and the installed `mattpocock/skills` copies (`.claude/skills/codebase-design/*.md`, `~/.claude/skills/*`); no page or skill file uses the term, so no primary source is cited for it. The applicable local principle is the skill's **locality**: "Change, bugs, knowledge, and verification concentrate in one place rather than spreading across callers" (`.claude/skills/codebase-design/SKILL.md:28`). For a catalogue, the unit of change is "add an input to panel X and print it on page Y", which touches one row in `inputs.ts` under either layout; the per-kind layout additionally keeps the id derivation local to one file. The repo's prior Pocock research records the same consumer-based ownership rule ("guidance for promoting an app module when it gains external consumers", `docs/research/2026-09-11-matt-pocock-repository-practices.md`, table row 2), which `apps/app/AGENTS.md:18-19` already encodes: "A feature starts beside its route and moves to `src/lib/<feature>/` when a second route imports it." Two routes import the definitions today (`projects/+page.svelte:10`, `projects/[projectId]/+page.svelte:25`), so the catalogue belongs at `apps/app/src/lib/definitions/` (name per `docs/trident/CONTEXT.md:139-141`, which reserves "definitions" and rejects "schema", "mirror", "snapshot"). The panel-grouped view the UI needs (`PanelInputGroupDefinitionType`, `projects.types.ts:257`; built in `projects.schema.ts:30-41`) is a derived lookup, computed once in `index.ts`, not a storage layout.

## 4. Where the 36 instructions rows go

`instructions.json` rows are `{ entity, name, type, description, notes, options, example }` keyed by column name, 36 rows across `global`, inputs, panels and pages; nothing in `apps/app/src` imports the file today (grep). That is documentation of the row types, and TypeScript already has a slot for it. Experiment `quickinfo.cjs` drove the TypeScript 6.0.2 language service (`createLanguageService().getQuickInfoAtPosition`) at the `id` and `order` properties of an object literal under each shape and read back the interface field's JSDoc in all three:

| Hover target | Quick info | Documentation returned |
| --- | --- | --- |
| property in `[...] as const satisfies readonly PanelDefinitionType[]` | `(property) PanelDefinitionType.id: string` | the interface field's JSDoc |
| property in `const q: readonly PanelDefinitionType[] = [...]` | same | same |
| property in `[...] satisfies readonly PanelDefinitionType[]` | same | same |

So `/** ... */` on each interface field carries `description`, `options` and `example` to wherever the row is edited, with no runtime cost. `svelte-check` itself is diagnostics only ("Provides CLI diagnostics checks for: Unused CSS, Svelte A11y hints, JavaScript/TypeScript compiler errors", [README](https://github.com/sveltejs/language-tools/blob/master/packages/svelte-check/README.md)); hover is the editor's language service, which for `.ts` files is TypeScript's. This pass verified TypeScript's service directly and did not drive the Svelte VS Code extension. The `entity`-scoped rows (an instruction that applies only to inputs) map to the field on that one interface; the `global` rows to the shared field on each. If the instructions are also wanted as data (a help panel, a seed table), keep them as a fourth `as const satisfies readonly InstructionDefinitionType[]` array; do not keep both without a test that they agree.

## 5. The seam: module import, not a remote function

svelte.dev, [remote functions](https://svelte.dev/docs/kit/remote-functions): "Remote functions are a tool for type-safe communication between client and server. They can be *called* anywhere in your app, but always *run* on the server, meaning they can safely access server-only modules." On `query`: "The `query` function allows you to read dynamic data from the server. For *static* data, consider using `prerender` functions instead." On `prerender`: "The `prerender` function is similar to `query`, except that it will be invoked at build time to prerender the result. Use this for data that changes at most once per redeployment." The feature remains "experimental ... subject to change without notice" (same page; also `docs/research/2026-09-18-sveltekit-3-status-and-fit.md` §2).

Today `fetchProjectDefinitions` (`projects.remote.ts:194-206`) is a `query` whose only reason to run on the server is three `fetch` calls to Sheetari (`projects.remote.ts:4-8`, `145-157`), and `CONTEXT.md:146-147` says the Report Generator "stops reading through it once the definitions live in the code". Once the rows are a TS module there is nothing server-only to protect and nothing dynamic to read: an `import { definitions } from '$lib/definitions'` is tree-shaken into the client bundle, needs no `await`, no request, and no `experimental.remoteFunctions` flag on this path. Per the codebase-design skill's deletion test (`SKILL.md`, "Principles"), deleting the remote function makes no complexity reappear anywhere. If a server-only source returns (a database of definitions, section 6), the docs' own answer for data that changes once per deployment is `prerender`, not `query`. `apps/app/AGENTS.md:29-36` ("Remote functions are the data layer") describes how the app reads *data*; definitions are code, and that file's `src/lib/<feature>/` row (`AGENTS.md:13`) already lists `.types.ts`/`.schema.ts` beside `.remote.ts` as peers, so a `definitions/` folder with no `.remote.ts` needs only a one-line note there.

Interface of the module, kept small: the three arrays, the three id unions, `inputsByPanel: ReadonlyMap<PanelIdType, readonly InputRowType[]>`, `pagesById`, `inputsById`. `createProjectSchema` (`projects.schema.ts:16`) keeps its signature and takes the module's `definitions` object; its title-based filters (`excludedSections = new Set(['Time Log'])`, `pageByName.get('Cover')`, lines 3, 52, 61-64) become id lookups in the same change.

## 6. Seeding a database later

Drizzle is the ORM named on #42. [Insert](https://orm.drizzle.team/docs/insert): multiple rows are `await db.insert(users).values([{ name: 'Andrew' }, { name: 'Dan' }])`; `onConflictDoNothing` "will cancel the insert if there's a conflict" and `onConflictDoUpdate` "will update the row if there's a conflict", with `target: users.id`, which is what makes a seed idempotent on string primary keys like `PANEL-001`. [Goodies, Type API](https://orm.drizzle.team/docs/goodies): `type InsertUser = typeof users.$inferInsert`, so a `satisfies readonly (typeof panelsTable.$inferInsert)[]` on the same literal proves the rows fit the table without a second type. [PostgreSQL column types](https://orm.drizzle.team/docs/column-types/pg): `pgEnum('mood', ['sad', 'ok', 'happy'])` takes the value list, and `text({ enum: [...] })` "infer[s] `insert` and `select` types, it **won't** check runtime values"; both accept the catalogue's `as const` unions and tuples, so `FieldInputType` and friends can be declared once as `as const` arrays and reused for the column. [drizzle-seed](https://orm.drizzle.team/docs/seed-overview) is for "deterministic, yet realistic, fake data" with `refine`; it is not the tool for real rows. Array-valued columns (`options`, `outputToPages`, `reference`) seed as `text().array()` or as join rows; the flat shape with string ids maps 1:1 either way, and the `instructions` rows seed from the JSDoc only if they are also kept as data (section 4). Nothing here needs deciding before #48; it only confirms the shape is not a dead end.

## 7. Recommendation

Create `apps/app/src/lib/definitions/` with `types.ts` (the three row interfaces, all fields `readonly`, arrays `readonly`, `InputDefinitionType<PanelId, PageId>` generic, every field carrying its instruction as JSDoc), `panels.ts`, `pages.ts` and `inputs.ts` (each `export const <kind> = [...] as const satisfies readonly <Row>[]` with `export type <Kind>IdType = (typeof <kind>)[number]['id']`, and `inputs.ts` ending in the `referencesResolve` guard), and `index.ts` (the generated barrel plus the derived `inputsByPanel`, `pagesById`, `inputsById`; if the generator cannot host derived values, put them in `definitions.ts` and let the barrel re-export). Rows reference panels and pages by **id**, converting the title-keyed JSON in the same change; the generator used in this research (`scratchpad/scale`) already performs the mapping and found zero unresolved references. Delete `fetchProjectDefinitions`, `fetchInputDefinitions`, `fetchPanelDefinitions`, `fetchPageDefinitions` and the Sheetari constants from `projects.remote.ts`, import the module in both pages, and move `createProjectSchema`'s title lookups to ids. Add `inputs.test.ts` that asserts referenced ids exist (naming the offender) and that `order` values are unique per kind. Leave `apps/app/src/lib/data/*.json` for the data (clients, team, photos) that is not a definition; remove `inputs.json`, `panels.json`, `pages.json`, `instructions.json` once the module lands so there is no second copy (`CONTEXT.md:148`, "local mirror (a copy nothing reads)").

## 8. What this does not decide

- Whether `instructions` is also kept as a fourth data array (needed only if a help UI or seed table wants it), and who owns agreement between it and the JSDoc.
- The database schema itself: tables, `pgEnum` vs `text({ enum })`, array columns vs join tables, and when the seed runs (#42's auth work).
- Whether the barrels generator (`packages/tools`) can emit the derived lookups or only re-export them.
- Changing `createProjectSchema`'s output shape (`ProjectSchemaType`) beyond swapping titles for ids; that belongs to "UI library cleanup" (#33), which `apps/app/AGENTS.md:38-42` already names for the two inline pages.
- Editor behaviour inside `.svelte` files was not driven in this pass; TypeScript's language service was.
